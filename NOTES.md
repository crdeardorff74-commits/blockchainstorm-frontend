## 2026-08-05 — Vibrancy part 2: vivid default, neutral well, neon bloom
- **`classicvivid` is now the default** (`DEFAULT_PALETTE_ID` in game.js; the `palettes[...]` fallbacks in color-palettes.js and the emergency COLORS array in `initColorsFromPalette` all point at it too — keep those three in step).
- **A migration was REQUIRED, not optional.** `initColorsFromPalette()` writes `tantro_palette` to localStorage on *every load*, so every returning player already has `'classic'` stored whether they ever chose it or not — changing the default alone would have reached brand-new browsers only. One-time flag `tantro_palette_vivid_v1` moves stored `'classic'` → `'classicvivid'` once; anyone who picks Classic back afterwards keeps it. (Downside accepted: someone who *deliberately* chose Classic is indistinguishable from someone who never chose, and gets moved. Same hues, so low harm.)
- **Well backdrop neutralised**: `rgba(30,60,120,0.25)` → `WELL_BACKDROP = 'rgba(8,12,28,0.30)'` (one constant, was duplicated in 3 places). Because faces draw at ~33% alpha, that wash was ~2/3 of what you see *through* every block — a blue floor that raises the minimum RGB channel of warm hues, which is precisely what kills saturation. Worth ~+21 points of on-screen saturation on the vivid yellow (49% → 70%) **with no palette change at all**. Still slightly above the starfield black so the well reads as a distinct rectangle.
- **Neon bloom shipped** as a Settings slider ("Glow", default 40%, `settings.glow` in all 15 languages). Strokes only the shape's EXPOSED perimeter — same adjacency the bevels use — blurred and additive, drawn BEFORE the blocks so they cover the inward half of the halo and only outward spill survives.
- **Why bloom is safe where the earlier additive face pass was not:** spill lands on the BACKDROP, not the face. The reverted attempt brightened faces additively, and brighter-at-the-same-saturation is the definition of washed out. Bloom leaves hues untouched and lights the surround.
- **Perf**: one blurred stroke per SHAPE, never per block (~200 shadowBlurs/frame would be unusable on mobile). 0% skips the pass entirely — that's the off switch for slow devices. Verified against the real shipped code with a mock ctx: single block = 4 segments, 2×2 square = 8 (interior edges skipped), 1×4 line = 10, glow 0% = 0 strokes.
- Bloom is mirrored in render-utils.js's `drawSolidShape` too, so leaderboard replays don't render flat beside live play. Like `borderBrightness` before it, that copy reads game.js's `glowStrength`/`GLOW_MAX_BLUR_RATIO` via `typeof` guards — note those are `let`/`const`, so `typeof` would NOT save it from a TDZ error if ever called before game.js finishes loading. Same pre-existing hazard as `borderBrightness`; safe only because drawing happens after load.
- Tuning knobs if it's over/under-done: `GLOW_MAX_BLUR_RATIO` (0.55 × blockSize at 100%), the slider default (40), and `WELL_BACKDROP`.

## 2026-08-05 — Palette vibrancy: `classicvivid` added; additive-glow render REVERTED
- **Goal**: the ChatGPT cover art reads far more vibrant than the game; make the default look closer to it.
- **⚠ FAILED ATTEMPT, DO NOT RETRY: a two-pass face (thin source-over body + additive `lighter` glow).** It made things visibly WORSE — the user's screenshot came back paler and flatter than before. Fully reverted; both `drawSolidShape` copies and the bevel shades are back to their original form, and the helper functions were deleted.
- **Why it failed, so nobody re-derives it:** the metric was wrong. Chroma measured as `max(RGB) − min(RGB)` roughly doubled, which looked like a win — but that number rises whenever a colour simply gets BRIGHTER. Additive light raises all three channels, so the *relative* saturation was unchanged while lightness shot up (`#FF6B6B` on screen went from max-channel 91 to 173). Lighter at the same saturation is the definition of washed out. **Judge palette work by HSL/perceptual saturation at a fixed lightness, never by absolute channel spread.**
- **The actual finding, which is the opposite of the first diagnosis:** Classic's colours are NOT under-saturated — most are already at 89-100% HSL saturation. They read pale because their **LIGHTNESS is 68-85%**. The cover art's colours sit at 45-59%, which is where hues are most vivid. So the palette IS the lever, specifically its lightness, and no compositing trick fixes a pastel.
- **Shipped instead: a new `classicvivid` palette** ("Classic Vivid", Standard category) — identical hues to `classic`, lightness range shifted −0.20 (clamped 0.40-0.66) with a 78% saturation floor for the two genuinely muted ones (green, purple). On-screen saturation 15-52% → 42-74%. Subset indices mirror `classic` exactly. **Zero render changes** — pure data.
- Luminance spread WIDENS (31-76 vs 58-84), so blobs stay tellable apart. That matters more here than in most games: matching colours IS the mechanic, not decoration. Both palettes already have near-zero minimum luminance gaps, so hue is what separates them either way.
- Added as a NEW palette rather than editing `classic` on purpose: it can be A/B'd in-game against the current default in one click, and promoting it to default afterwards is a one-line change (`game.js` `currentPaletteId` fallback). Also avoids changing the default mid-trial-prep.
- Still-untried levers if more punch is wanted: the well's `rgba(30,60,120,0.25)` blue veil (it specifically neutralises warm hues), and a real bloom pass (outline `shadowBlur`) — the latter deferred as a mobile perf risk that would want its own Settings slider + 15 i18n keys.

## 2026-08-05 — Conversion denominator: page-load record
- **`Analytics.recordPageLoad(ctx)`** fires immediately at load, NOT waiting for an interaction — the visit POST is gated on one, so it can never see someone who loads and leaves. Called from game.js's visit-tracking block (device/OS classification already lives there); the visit POST now also carries `Analytics.getLoadId()`.
- **`page_visits` behaviour is completely unchanged** — the interaction gate stays, so the historical start rate remains comparable. See the back-end NOTES for why merging the two would be a mistake.
- **Queue extension worth knowing about:** load entries are the ONE kind with no `visitId`. `loadQueue()` drops null-visitId entries as unresolvable orphans, so load records are explicitly exempted there, in `send()`, in `flushQueue()`, and in `setVisitId()` (which must not stamp them). A new entry kind needs the same four touch points.
- **Hidden loads are deferred, not dropped**: a prerender or background tab isn't an impression, so the record waits for the first `visibilitychange → visible`. If the page is never seen, nothing is sent.

## 2026-08-05 — Batch 3: controls discovery (input instrumentation)
- **`Analytics.control(token)`** — same one-shot-per-visit mechanism as `flag()` but its own set/column, because menu exploration and control discovery are different questions. Tokens: `src_kbd`, `src_touch`, `src_btn`, `act_move`, `act_rot`, `act_hard`.
- **THE trap, and why this batch was held to last:** the action functions (`rotatePiece`, `rotatePieceCounterClockwise`, `movePiece`, `hardDrop`) are ALSO called by the AI demo loop and by replay playback. Un-gated, an AI demo would report flawless control discovery for a player who never touched anything. All four route through `trackControlAction()`, which carries the same `aiModeEnabled || GameReplay.isActive()` gate `gameOver()` uses. **Never call `Analytics.control()` from an action function directly — go through the helper.**
- Source tokens are hooked at the INPUT layers instead (keydown in game.js gated on `gameRunning && !paused`, `handleStart` in touch-controls.js *after* its existing UI-element guards, and both button helpers) because those are only ever driven by a real human — no gating needed there.
- `addTouchAndClick` now wraps its handler to record `src_btn`; checked first that nothing does `removeEventListener` with the original reference (only the document-level gesture handlers are ever removed, via `this._on*`).
- **Soft drop is deliberately NOT measured.** There's no single `softDrop()` seam — touch has `startSoftDrop`, keyboard mutates `currentPiece.y` inline — so it could only be captured for some input methods, which would read as "keyboard players never soft-drop". Better absent than structurally wrong. Rotate + hard drop are the discovery signals that matter.
- `src_pad` is NOT recorded client-side: the older `/gamepad` endpoint already sets `page_visits.used_gamepad`, and the summary folds that in server-side rather than double-recording.

## 2026-08-05 — CrazyGames engagement instrumentation (batch 1 of 3)
- **Why**: submitting to CrazyGames; a Basic Launch trial grades playtime / D1 / conversion and TANTЯO measured none of them. Source list is `CRAZYGAMES.md` §5 at the umbrella root (its §0 lesson: ship analytics BEFORE the trial). Batch 1 = session+play clocks, per-game outcome rows, abandonment beacon, delivery robustness. **Still to do: D1 cohorts + onboarding funnel (batch 2), mobile controls-discovery (batch 3 — deliberately last and alone, it's the only one touching `touch-controls.js`/input handlers, so a regression stays isolable).**
- **New `analytics.js`** (loads 2nd, right after config.js; self-inits like ErrorBoundary). Decisions worth keeping: a game row is written at START as `in_progress` — the sessions that vanish are exactly the ones worth measuring AND the least likely to deliver an exit beacon; `end_cause` only ever climbs in_progress→abandoned→game_over so a late duplicate can't demote a finished game; AI demo games and replays are excluded at every call site (`!aiModeEnabled` — they run `gameRunning=true` and would pour attract-mode minutes into the playtime average); resumed-from-save games carry `resumed:true` and are excluded from charts (their clock restarts at zero).
- **Trap that cost the most thought — `sendBeacon` content type.** A Blob typed `application/json` triggers a CORS preflight, and a beacon fired during page teardown cannot complete one → every exit beacon would silently vanish cross-origin (i.e. in production). Beacons now send `text/plain;charset=UTF-8` and the back end parses with `get_json(force=True)`. **These two are a matched pair — change one and telemetry dies silently.** There's a test asserting the type.
- **Deliberately NOT changed: the visit-row trigger.** It stays interaction-gated (≥1s post-load), so our start rate keeps the same denominator as the 3,896 historical visits. Fixing the CG-conversion mismatch has to be additive (a load counter / `interacted` flag), per the playbook's "metrics whose definition you changed" trap. Open item for batch 2.
- **Closing the whole BROWSER (not the tab) loses the exit beacon** — found in first live testing: the browser process that would carry an in-flight `sendBeacon` dies with it, so a cold Render dyno never receives it, and the row sits at `in_progress` with duration 0s until that browser next loads the game and flushes its queue. Unfixable at the transport layer. Mitigation shipped: **backstop syncs while the game runs** on an escalating schedule (`SYNC_STEPS_MS` = 15/30/60/120s, ticked every 15s) so an unheard-from game still carries a real duration as a lower bound. Early steps are close together because that's where abandons happen.
- **`abandoned` and `in_progress` are the SAME player act** — TANTЯO has no quit button, so both mean "left mid-game"; they differ only in whether the beacon survived. The admin panel's original "Quit mid-game" / "No closing beacon" labels implied two different behaviours; relabelled "Left mid-game (confirmed)" / "(beacon lost)" with a combined total. Don't reintroduce a reading where they're distinct outcomes.
- **Tests**: `tantro/tests/analytics-delivery.test.js` (23 assertions, node-only, no deps — universal rule 11). Run it after touching analytics.js; it guards the clocks, the queue's keep-vs-drop rules, and the idempotency key. Not browser-verified per rule 0.
- **Needs `/rel` + zip**: `analytics.js` is a new file and is in `sw.js` CORE_ASSETS — the version bump is what busts the SW cache and actually gets it to players.
