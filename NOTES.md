## 2026-08-05 — Music-at-game-over tracking + histogram bucket order fix
- **BUG: the Game length chart was ordered alphabetically** (`0-14s, 1-2m, 10m+, 15-29s, …`). Cause: the histograms are dicts and **Flask's `jsonify` SORTS dict keys**, so the admin panel's `Object.keys(hist)` walked alphabetical order no matter how the dict was built. Fixed server-side by exporting `DURATION_BUCKET_LABELS` as an ordered LIST (which survives serialization) and having the panel iterate that. **Any future ordered data crossing this API must be a list, not dict key order.**
- **New: `game_results.music_on`** — was gameplay music AUDIBLE when the game ended. Stricter than "a track is selected": muted, volume zero, paused, or no track ever loaded all count as off, because the question is whether the soundtrack is actually reaching people.
- **Read BEFORE `stopMusic()`**, which runs a few lines later in `gameOver()`. Called any later and the answer is always false. (`setGameInProgress(false)` runs earlier but only sets a flag, so it is safe.)
- **Only the game-over payload carries `musicOn`** — `in_progress`/`abandoned` payloads omit the key entirely (JSON.stringify drops undefined), and the server assigns only when the key is present. So a backstop sync or a late duplicate beacon can never blank out a recorded value.
- **The rate is over FINISHED games, never all games.** An abandoned game never reports music state; folding those in would read as "music off" and roughly halve the number. NULL is likewise not "off" — it means the game never got that far. Mutation-verified in the test suite.
- Column is nullable and added via the startup `ADD COLUMN IF NOT EXISTS` block — no manual migration.

## 2026-08-05 — Automatic effect reduction on slow devices (`PerfGuard`)
- **Reported to analytics as the `perf_reduced` control token**, emitted from `apply()` so it covers BOTH paths — the moment the guard fires and the re-apply on a device already judged slow. The metric therefore reads "sessions running reduced", not "sessions where it fired today". No back-end change was needed: `control_flags` is a generic union-merged token set and `summarize()` already tallies arbitrary tokens among played sessions (which is the right denominator, since the guard only runs during gameplay). Surfaced on its own line in the admin Controls block, above the input mix, because it describes the DEVICE rather than how the player played.
- **Why report it at all:** the 22ms threshold is a judgement call made without slow hardware to test on. Unreported it is unfalsifiable — too eager and mid-range phones silently lose the glow, too lax and it never runs. If this reads high on phones during the trial, the glow default is too expensive for that audience.
- **BUG FIXED same day:** Reset to Defaults called `selectPalette('classic')` — a hardcoded id missed when the default moved to `classicvivid`, so resetting quietly reverted players to the retired look. Now `selectPalette(DEFAULT_PALETTE_ID)`, with a regression test (mutation-verified). Two other `'classic'` literals were deliberately LEFT alone: the fallbacks in `game-recorder.js` and `replay.js` apply to recordings that carry no palette field, and those are genuinely old classic-era recordings.
- **Why, given there's already a Glow slider:** a slider only helps players who go looking for it, and this project's own funnel instrumentation exists because Circuitousness found ~9.2% ever open a menu. On a weak phone the damage is done in the first thirty seconds, and CrazyGames scores mobile as its own 15 points. The game has to notice for itself.
- Measures the **median** frame time over a window of real gameplay (120 warm-up frames, then 120 judged). Above ~22ms (roughly 45fps) it sets Glow to 0 and Opacity to 33 — opacity rises because the faces have to carry the piece once the rim light is gone.
- **Median, not mean, and an outlier cap at 500ms**: a GC pause or tab switch must not condemn a device that is otherwise keeping up. The warm-up exists because asset decode and first paint are always slow.
- **Applied THROUGH the sliders with synthetic (untrusted) events.** Two reasons, both load-bearing: Settings then shows the truth, and the `isTrusted` hook does not record it as a player choice — if it did, that device would be frozen out of every future change to those defaults.
- **An explicit Glow choice outranks the guard in both directions**: it never measures, and a stored reduction never overrides the choice. Raising Glow back up after a reduction is how the player says "I know, I want it anyway", and it sticks. No fight with the user.
- **Remembered in `localStorage` ONLY (`tantro_perf_degraded_v1`), never the synced settings blob** — performance is a property of the device, not the account. A slow phone must not drag down the same player's desktop.
- Sampling is gated at the call site to unpaused human play: a paused board renders nothing and would read as fast, and AI-demo/replay frames aren't the player's device under load.
- **Untested on real slow hardware** (none available). That's precisely why `tantro/tests/perf-guard.test.js` exists — 15 assertions, mutation-verified against mean-instead-of-median, no-warm-up, and ignoring the player's choice. Thresholds are read out of game.js by the harness, so retuning them doesn't invalidate the tests.

## 2026-08-05 — New look defaults + a way for future defaults to actually reach players
- **New defaults: Opacity 11%, Glow 42%, Border 130%, Thickness 16%** (user-tuned by eye; re-tuned once from 7/50/122/19 before anything shipped). `SETTING_DEFAULTS` in game.js is now THE source of truth, in slider units; index.html's `value=` attributes and the placeholder `faceOpacity` in render-utils.js/histogram.js mirror it for first paint. Reset to Defaults is driven from the same map, so there is one place to change a default.
- **THE PROBLEM this solves:** settings-sync writes a value for EVERY slider whenever any one of them changes, so a saved blob is not evidence that the player chose anything — everyone has a stored value for everything. Changing a default therefore reached brand-new browsers only. (Exactly the same trap as `tantro_palette`, written on every load.)
- **The fix: record intent separately.** A slider counts as chosen only when a REAL gesture moves it — `event.isTrusted`, which is what distinguishes a player dragging a slider from the synthetic `input` events dispatched by settings restore and by Reset to Defaults. **Neither of those may ever mark a slider as chosen, or defaults stop propagating forever.** On restore, settings-sync honours the stored value only for chosen sliders; everything else follows the current default.
- The chosen-set rides inside the settings blob as `_touched`, so it syncs to the server for logged-in players. Without that, a choice made on one device would look like an untouched default on every other.
- **`SETTINGS_EPOCH` = one-time override.** Bumping it forgets every recorded choice once, so the new defaults win even where a player had set their own. Now at **2** — the rim glow changed the whole dynamic of the piece rendering, and old opacity/border values were chosen against a look that no longer exists. **Reserve future bumps for changes that make an old value read as broken rather than as a preference**; a bump discards real player choices.
- **To change a default later: edit `SETTING_DEFAULTS` (and the matching `value=` in index.html) and ship. Do NOT bump the epoch** — the mechanism above already carries it to everyone who never set that slider.
- **Re-tuning is a 4-file change** (`SETTING_DEFAULTS` in game.js, `value=` + the display span in index.html, and the placeholder `faceOpacity` in render-utils.js and histogram.js). A test asserts game.js and index.html AGREE — a desync shows as sliders visibly jumping on load, since index.html paints first. There is a `retune.py` in the session scratchpad that does all four with assertions; the test is the durable guard.
- Tests: `tantro/tests/settings-defaults.test.js` (13 assertions). Two of them grep settings-sync.js and game.js for the wiring, because the suite's `restore()` mirrors settings-sync's DOM-bound loop rather than executing it. Mutation-verified: removing the `isTouched` gate fails the suite.

## 2026-08-05 — Line endings normalised to LF (whole project)

Deliberately narrow — no trailing-whitespace or final-newline rules, which would make editors reformat large files on save.

## 2026-08-05 — Vibrancy part 2: vivid default, neutral well, neon bloom
- **`classicvivid` is now the default** (`DEFAULT_PALETTE_ID` in game.js; the `palettes[...]` fallbacks in color-palettes.js and the emergency COLORS array in `initColorsFromPalette` all point at it too — keep those three in step).
- **A migration was REQUIRED, not optional.** `initColorsFromPalette()` writes `tantro_palette` to localStorage on *every load*, so every returning player already has `'classic'` stored whether they ever chose it or not — changing the default alone would have reached brand-new browsers only. One-time flag `tantro_palette_vivid_v1` moves stored `'classic'` → `'classicvivid'` once; anyone who picks Classic back afterwards keeps it. (Downside accepted: someone who *deliberately* chose Classic is indistinguishable from someone who never chose, and gets moved. Same hues, so low harm.)
- **Well backdrop neutralised**: `rgba(30,60,120,0.25)` → `WELL_BACKDROP = 'rgba(8,12,28,0.30)'` (one constant, was duplicated in 3 places). Because faces draw at ~33% alpha, that wash was ~2/3 of what you see *through* every block — a blue floor that raises the minimum RGB channel of warm hues, which is precisely what kills saturation. Worth ~+21 points of on-screen saturation on the vivid yellow (49% → 70%) **with no palette change at all**. Still slightly above the starfield black so the well reads as a distinct rectangle.
- **Neon rim glow shipped** as a Settings slider ("Glow", default 40%, `settings.glow` in all 15 languages). `paintRimGlow()` in game.js lights the inside of each blob's rim, fading inward: bright at the edge, dark toward the middle. Nothing spills outside the shape and the middle is never lifted — that was the failure of the reverted additive-face pass.
- **⚠ It is a DISTANCE FIELD on an offscreen layer, composited ONCE. Do not replace it with per-edge geometry.** Build: (1) fill the shape's FACE silhouette — each block inset by the bevel `b` on whichever sides are exposed, interior sides left full so adjacent faces join; (2) erase the interior with `destination-out` using a BLURRED copy of that same silhouette; what survives is exactly `1 - blur(silhouette)`, a smooth rim identical all the way round; (3) `drawImage` once, additively. Callers need no clip — the layer cannot paint over the bevel or outside the shape by construction.
- **The blurred copy is made as a SHADOW, not with `ctx.filter`.** The silhouette is drawn far off the left of the scratch canvas and its shadow offset back into place. `ctx.filter = 'blur()'` would be simpler but Safari only supports it from 17, and on older iOS the erase would run unblurred and wipe the glow out entirely.
- **⚠ FOUR per-edge approaches were tried before this and every one left a visible artefact. The rock they all hit: any per-edge method must decide what happens where two edges' bands meet, and every answer shows.**
  1. `shadowBlur` on a thin perimeter stroke — INVISIBLE. A Gaussian conserves energy: a 2.4px line blurred over 19px peaks at ~3% after alpha, while the unblurred stroke under it still reads as a hard line. Widening the blur makes it strictly worse.
  2. Stacked strokes of decreasing width — bright (peak 0.36 vs 0.034) but only N steps, and **the banding was plainly visible**.
  3. Per-edge gradient bands, `'lighter'` (added) — bands overlap near corners and the sum made **a bright rectangle with straight sides**.
  4. Same bands, `'lighten'` (max) — subtler, but the weight difference between adjacent sides still **stepped at every corner**.
- **The glow is isotropic on purpose.** Every attempt to give it a directional bias (`GLOW_SIDE_WEIGHT`) reintroduced a step wherever two differently-weighted edges met. The BEVEL carries the light direction; the glow does not need to.
- **⚠ INNER (concave) corners need their own punch-out — a per-side inset cannot express them.** `drawSolidShape` fills a `b×b` square at each concave corner with two 45° triangles (its `T && L && !TL` blocks and the three rotations). The glow's face silhouette is built from per-block rects inset on exposed sides, which does not exclude those squares, so the glow painted straight over the inner-corner bevels. Step 1b now `destination-out`s a `b×b` square at each. Verified: an L-tromino with one concave corner emits exactly one 6×6 punch-out at the right block; a 1×2 bar emits none and skips the step.
- The blur in step 2 deliberately uses the UN-notched silhouette, so the falloff flows smoothly past a concave corner instead of treating a 6px notch as an edge. The notch is punched out of the fill either way, so it stays transparent.
- **The bevel must never be under the glow's brightest point.** Starting the glow at the block boundary flooded all four bevel shades to one value and turned the bevel into a uniform thick outline. The face-silhouette inset is what protects it — and doing that by trimming band ends instead (an earlier attempt) is what produced the blocky seams.
- **Pixel coordinates MUST come from the block's real position, never from `ry`.** `ry = Math.round(y)` is for adjacency tests ONLY. Deriving pixels from it quantised the glow to whole cells, so a falling piece's glow sat still and jumped a row at a time while the piece moved smoothly.
- Verified against the shipped function with a recording stub (S-piece, 30px blocks, 6px bevel): 2 scratch fills (`source-over` silhouette, then `destination-out` blur 17.8px at shadowOffsetX 176 with the source at x=−124, fully off-canvas), exactly 1 `drawImage` at alpha 0.72 — the 2× normalises the rim's natural 0.5 peak back to the requested 0.36 — and adjacent blocks' faces touching exactly (block (1,0) ends at y=30, (1,1) starts at y=30) with exposed sides inset by 6.
- **The histogram bars glow too**, via the same code. `paintRimGlow` is split into a grid-aware front end and `paintRimGlowRects(ctx, rects, notches, color, strength, reach)` — the offscreen machinery over plain rectangles. histogram.js's `drawBarGlow()` calls the latter with the bar's single face rect (bar inset by its bevel on all four sides) and `notches = null`; a bar has no concave corners. Added after all FOUR `drawBarCorners` sites: the horizontal bar, the speed-bonus bar, the score histogram and the colour histogram.
- Bar `reach` scales with the bar's SHORT side (`Math.min(fw, fh) * GLOW_REACH_RATIO * strength`). These bars are thin; a reach sized off the long side would flood a whole bar with glow.
- histogram.js reads `glowStrength`, `GLOW_REACH_RATIO` and `paintRimGlowRects` through `typeof` guards, exactly as it already does for `borderBrightness` — it is loaded before game.js.
- Scratch canvas is module-level and GROW-ONLY (`_glowCanvas`): resizing a canvas clears it, so resizing per frame would be both slow and wrong. Only the needed `w×h` sub-rect is cleared and sampled, so stale pixels beyond it are harmless.
- **Perf**: per shape, one clear + two fills + one `drawImage`, and one shadow-blur over the shape's bbox. Heavier than the per-edge versions it replaced, but per SHAPE (~10-40 a frame), never per block. 0% skips the pass entirely, so the slider is a real off switch for slow devices — worth checking on a phone.
- The glow is mirrored into render-utils.js's `drawSolidShape` so leaderboard replays and the next-piece preview don't render flat beside live play. ## 2026-08-05 — Palette vibrancy: `classicvivid` added; additive-glow render REVERTED
- **Goal**: the ChatGPT cover art reads far more vibrant than the game; make the default look closer to it.
- **⚠ FAILED ATTEMPT, DO NOT RETRY: a two-pass face (thin source-over body + additive `lighter` glow).** It made things visibly WORSE — the user's screenshot came back paler and flatter than before. Fully reverted; both `drawSolidShape` copies and the bevel shades are back to their original form, and the helper functions were deleted.
- **Why it failed, so nobody re-derives it:** the metric was wrong. Chroma measured as `max(RGB) − min(RGB)` roughly doubled, which looked like a win — but that number rises whenever a colour simply gets BRIGHTER. Additive light raises all three channels, so the *relative* saturation was unchanged while lightness shot up (`#FF6B6B` on screen went from max-channel 91 to 173). Lighter at the same saturation is the definition of washed out. **Judge palette work by HSL/perceptual saturation at a fixed lightness, never by absolute channel spread.**
- **The actual finding, which is the opposite of the first diagnosis:** Classic's colours are NOT under-saturated — most are already at 89-100% HSL saturation. They read pale because their **LIGHTNESS is 68-85%**. The cover art's colours sit at 45-59%, which is where hues are most vivid. So the palette IS the lever, specifically its lightness, and no compositing trick fixes a pastel.
- **Shipped instead: a new `classicvivid` palette** ("Classic Vivid", Standard category) — identical hues to `classic`, lightness range shifted −0.20 (clamped 0.40-0.66) with a 78% saturation floor for the two genuinely muted ones (green, purple). On-screen saturation 15-52% → 42-74%. Subset indices mirror `classic` exactly. **Zero render changes** — pure data.
- Luminance spread WIDENS (31-76 vs 58-84), so blobs stay tellable apart. That matters more here than in most games: matching colours IS the mechanic, not decoration. Both palettes already have near-zero minimum luminance gaps, so hue is what separates them either way.
- Added as a NEW palette rather than editing `classic` on purpose: it can be A/B'd in-game against the current default in one click, and promoting it to default afterwards is a one-line change (`game.js` `currentPaletteId` fallback). Also avoids changing the default mid-trial-prep.
- Still-untried levers if more punch is wanted: the well's `rgba(30,60,120,0.25)` blue veil (it specifically neutralises warm hues), and a real bloom pass (outline `shadowBlur`) — the latter deferred as a mobile perf risk that would want its own Settings slider + 15 i18n keys.
